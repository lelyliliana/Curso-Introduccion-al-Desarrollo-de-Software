# Ingeniería de sistemas y de software

[Recurso anterior](../../unidad-1/02-ingenieria-y-decisiones/README.md) · [Índice de la unidad](../README.md) · [Siguiente recurso](../../unidad-1/04-proceso-de-software/README.md)

## Objetivo

Distinguir disciplinas y asignar responsabilidades en un proyecto.

## Conceptos y explicación

La ingeniería de sistemas estudia y coordina sistemas con elementos e interacciones, incluidos componentes humanos, físicos y digitales. La ingeniería de software se concentra en especificar, desarrollar, verificar, operar y mantener software de manera sistemática. Se relacionan, pero no son sinónimos exactos. El nombre de un programa académico de ingeniería de sistemas puede tener un alcance informático particular según su contexto.

Programar implementa una parte de la solución; analizar necesidades, administrar infraestructura, diseñar pruebas y acompañar operación son responsabilidades diferentes. En equipos pequeños una persona puede asumir varias, pero deben seguir siendo visibles. El nombre de un cargo no garantiza una competencia ni reemplaza la responsabilidad por la calidad.

Las decisiones tienen efectos sobre personas. Un dato innecesario aumenta la exposición de información; una interfaz que depende solamente del color dificulta su uso. La accesibilidad, privacidad, comunicación y mantenimiento deben considerarse desde el inicio. La documentación debe permitir que otro integrante comprenda una decisión sin depender de la memoria de quien la tomó.

## Caso resuelto paso a paso

Para gestionar kits se distribuye el trabajo:

| Responsabilidad | Producto verificable |
|---|---|
| Análisis | Reglas de disponibilidad y devolución |
| Diseño | Modelo de estados y datos |
| Desarrollo | Funciones que implementan reglas |
| Pruebas | Casos de disponible, agotado y duplicado |
| Operación | Instrucciones de respaldo y recuperación |

Si se registra el nombre completo de cada estudiante sin necesitarlo para el ejercicio, se introduce información personal innecesaria. En las prácticas del curso se usan identificadores ficticios.

## Práctica guiada

Asocia cada requisito con un responsable de revisarlo. Describe qué evidencia entregará. Examina una decisión que afecte a usuarios con necesidades distintas. Sustituye datos reales por datos sintéticos en los ejemplos.

## Errores que conviene detectar

- Tratar ingeniería de sistemas e ingeniería de software como nombres intercambiables en cualquier contexto.
- Creer que privacidad y accesibilidad son responsabilidad exclusiva de otro integrante.

## Ejercicio para resolver

Distribuye responsabilidades para una agenda de tutorías. Identifica una decisión de privacidad y una de accesibilidad, con una prueba para cada una.

<details>
<summary>Solución y razonamiento (abre después de intentarlo)</summary>

Análisis define cupos y cancelación; desarrollo implementa reglas; pruebas revisa duplicados y límites; operación verifica recuperación. Usa códigos ficticios y prueba que los datos de ejemplo no identifiquen personas. Para accesibilidad, muestra mensajes textuales de error y verifica que la información no dependa de rojo o verde.

</details>

## Preguntas de comprensión

¿Desarrollar software incluye mantenerlo? ¿Una responsabilidad requiere siempre una persona diferente? ¿Cómo se verifica una decisión de accesibilidad?

## Evidencia de aprendizaje

Entrega tu desarrollo del ejercicio, el razonamiento o prueba de escritorio y al menos un caso límite. Explica cualquier cambio de contrato. Conserva los resultados que permitan comprobar tu conclusión.
